# 03. 텍스처 / 팔레트 / 머티리얼 (GFX, PAL, TXR, MAT)

도구: `devple.gow.tools.texture` 패키지

```bash
./gradlew -q :tools:run --args="texture:info   gow-rom/R_HERO0.WAD"             # 텍스처 표
./gradlew -q :tools:run --args="texture:export gow-rom/R_HERO0.WAD work/textures/R_HERO0 [--preview]"
./gradlew -q :tools:run --args="texture:mat    gow-rom/ATHN07.WAD"              # 머티리얼 레이어 표
./gradlew -q :tools:run --args="texture:check  gow-rom"                         # 전체 WAD 일괄 검사
./gradlew -q :tools:run --args="texture:mipcheck gow-rom"                       # 스위즐 판별 통계
```
`--preview` 는 알파를 체커보드 위에 합성한 불투명 PNG 를 만든다 (흰 글꼴처럼 알파로만 형태가 드러나는 텍스처 확인용).

| 클래스 | 역할 |
|-------|------|
| `GfxResource` | GFX_/PAL_ 파서 (record) |
| `TextureResource` | TXR_ 파서 |
| `MaterialResource` | MAT_ 파서 (+ `Layer`) |
| `TextureDecoder` | 인덱스/CLUT → ARGB, CSM1 해제, PSMT8 스위즐 해제, 알파 확장 |
| `GsSwizzle` | GS 로컬 메모리 배치 에뮬레이션 (PSMCT32 쓰기 → PSMT8 읽기). 공식 검증용 |
| `TextureLibrary` | WAD 단위 이름 해석 (TXR → GFX/PAL, 밉 레벨 팔레트 상속) |
| `Cli` | `texture:*` 명령 |

## 1. 리소스 관계

```
MAT_xxx ──layer.texture──▶ TXR_xxx ──gfx──▶ GFX_xxx  (인덱스 이미지)
                               │  └──pal──▶ PAL_xxx  (CLUT, 같은 포맷)
                               └─nextMip─▶ TXR_xxx2 ──gfx──▶ GFX_xxx2 (1/2 크기, pal 비어 있음)
```
WAD 안에서는 의존 순서대로 `GFX_ → PAL_ → TXR_` 이 이어지고, 밉 체인은 작은 레벨의 TXR 이 먼저 나온다.
MAT_ 는 주로 MDL_ 의 GROUP 안에 들어 있다.

## 2. GFX_ / PAL_ (리소스 매직 0x0C, 태그 flags=3)

이미지와 팔레트가 **같은 헤더**를 쓴다. 팔레트는 bpp=32 인 작은 이미지일 뿐이다.

| 오프셋 | 타입 | 필드 | 의미 |
|-------|------|------|------|
| 0x00 | u32 | magic | `0x0000000C` |
| 0x04 | u32 | width | 픽셀 |
| 0x08 | u32 | height | 픽셀. **frames 개 서브 이미지를 세로로 쌓은 전체 높이** |
| 0x0C | u32 | flags | 0 또는 2. **bit1(=2) = 선형(스위즐 안 됨)** |
| 0x10 | u32 | bpp | 4 (PSMT4), 8 (PSMT8), 32 (팔레트 RGBA) |
| 0x14 | u32 | frames | 서브 이미지 수: 이미지는 애니메이션 프레임(20, 50), 팔레트는 CLUT 개수(1, 2) |
| 0x18 | u8[] | data | `width*height*bpp/8` 바이트 |

### 전수 통계 (214 WAD)
| 종류 | bpp | flags | frames | 개수 |
|------|-----|-------|--------|------|
| PAL | 32 | 0 | 1 | 6616 |
| PAL | 32 | 0 | 2 | 77 |
| GFX | 8 | 0 | 1 | 6011 |
| GFX | 4 | 0 | 1 | 872 |
| GFX | 8 | 2 | 1 | 104 (전부 R_PERMK) |
| GFX | 4/8 | 0 | 20, 50 | 25 (풀 흔들림 `plantGrass200` 128x1280 = 128x64x20, 하늘 `skySold00` 64x800 = 64x16x50) |

- 모든 리소스에서 `size - 0x18 == width*height*bpp/8` 이 성립 → 헤더 0x18 바이트 확정, 밉 레벨은 GFX 안에 같이 들어 있지 않음.
- PSMCT16/24/32 직접색 이미지는 **게임 전체에 하나도 없다** (디코더는 대비용으로만 지원).
- WAD 선언부의 `GFXX_<wad>` (서버 선언, 매직 `0x8000000C`) 는 GFX 가 아님.

### 팔레트(CLUT)
- 4bpp → 16색 = 8x2, 8bpp → 256색 = 16x16. frames=2 면 16x32 (CLUT 2개, 위→아래).
- 엔트리 = R,G,B,A 바이트 (PSMCT32).
- **알파는 0..0x80** (0x80 = 불투명). 전수 조사 시 상위 니블이 8 을 넘는 알파 없음 → `a >= 0x80 ? 255 : a*255/128`.
- **256색 CLUT 은 CSM1 배치**로 저장: 32엔트리 블록마다 8–15 ↔ 16–23 교환.
  `실제 = (i & ~0x18) | ((i & 0x08) << 1) | ((i & 0x10) >> 1)`
  - 근거: 표본 WAD 22개(10개마다 1개)의 8bpp 이미지 1225개에 대해 인접 픽셀 색 차이 합을 비교 → CSM1 적용이 1223개에서 더 매끄러움, 반대는 2개.
  - 16색 CLUT 은 교환 없음.
- CLUT 2개 팔레트 예: `PAL_MAI01F` (R_HERO0, Kratos 몸) — 두 번째는 **회색조 버전** (메두사 석화 효과용으로 추정).

### 픽셀 배치 (스위즐)
| 포맷 | flags=0 | flags=2 |
|------|---------|---------|
| PSMT4 | 선형 (바이트당 하위 니블 = 왼쪽 픽셀) | (사례 없음) |
| PSMT8 | **PSMCT32 스위즐** | 선형 |

PSMT8 데이터는 "PSMCT32 형식 (w/2 x h/2) 로 GS 에 전송하면 메모리 안에서 올바른 PSMT8 텍스처가 되도록" 미리 섞여 있다
(PS2 에서 4배 빠른 32비트 전송을 쓰기 위한 흔한 기법). 픽셀 (x,y) 의 원본 바이트 위치:

```
block   = (y & ~15) * w + (x & ~15) * 2
swap    = (((y + 2) >> 2) & 1) * 4
posY    = (((y & ~3) >> 1) + (y & 1)) & 7
column  = posY * w * 2 + ((x + swap) & 7) * 4
byte    = ((y >> 1) & 1) + ((x >> 2) & 2)
src     = block + column + byte
```

근거:
1. 처음 선형으로 디코드한 Kratos 텍스처(`GFX_MAI01F`)가 행이 엇갈려 줄무늬로 나옴 → 위 식 적용 후 정상.
2. `GsSwizzle` 로 GS 메모리(페이지 8KB / 블록 256B, PSMCT32·PSMT8 블록·컬럼 테이블)를 에뮬레이션해
   "PSMCT32 쓰기 → PSMT8 읽기" 결과가 위 식과 w≥16, h≥4 인 모든 크기에서 100% 일치함을 확인.
3. **밉 체인 검증** (`texture:mipcheck`): 상위 레벨을 2x2 평균 축소한 이미지와 하위 레벨을 선형/스위즐로 각각 디코드해 오차 비교
   → 폭 16 이상인 flags=0 PSMT8 밉 360여 개 전부(16x4 ~ 256x64) 스위즐 쪽이 압도적으로 오차가 작음 (예: 16x4 선형 57.9 vs 스위즐 2.9).
4. R_PERMK 의 HUD/이펙트 텍스처(flags=2)는 스위즐을 적용하면 깨지고 선형으로 읽으면 정상 → flags bit1 = 선형.
5. PSMT4 (flags=0) 는 선형으로 읽은 결과가 정상 (`GFX_Comicsmoke`, 한글 폰트 `GFX_GOWK_*`, 풀 애니메이션 등).

## 3. TXR_ (매직 0x07, 크기 0x58, 태그 flags=0)

| 오프셋 | 타입 | 필드 | 의미 |
|-------|------|------|------|
| 0x00 | u32 | magic | `0x00000007` |
| 0x04 | char[24] | gfx | GFX_ 이름 |
| 0x1C | char[24] | pal | PAL_ 이름. 밉 레벨 TXR 은 빈 문자열 (상위 텍스처 팔레트 공유) |
| 0x34 | char[24] | nextMip | 다음 밉 레벨 TXR_ 이름 (가로·세로 1/2). 없으면 빈 문자열 |
| 0x4C | s32 | mipK | GS `TEX1.K` (LOD 바이어스, 1/16 단위 고정소수)로 추정 |
| 0x50 | f32 | mipL | LOD 관련 값 (거리/스케일로 추정) |
| 0x54 | u32 | flags | 아래 표 |

- 한 GFX 를 여러 TXR 이 공유하는 경우가 많다 (`GFX_woodPlanks06a` ← TXR 4개). 이름이 같은 TXR 이 한 WAD 에 여러 번 나오기도 한다 (`R_PERMK` 의 `TXR_file1`).
  → 이름 해석은 "참조하는 태그 앞의 가장 가까운 같은 이름 리소스" 로 한다.
- nextMip 체인 실측: `GFX_MAStatue01 256x128 → 012 128x64 → 013 64x32`.
- **mipK / mipL 규칙성** (R_PERMK HUD): 텍스처 최대 변 S 에 대해 `K = -16*(log2 S + 2)`, `L = 64 + S/8`
  (8→-80/65, 32→-112/68, 128→-144/80, 256→-160/96). 레벨 텍스처는 -128/256.0, -144/512.0 등 다른 상수.
  K 는 GS TEX1.K 포맷(부호 7.4 고정소수)과 맞아떨어짐 (-144 = -9.0).

| flags 값 | 개수 | 관찰 |
|---------|------|------|
| 0x00010000 | 10418 | 기본. bit16 은 항상 1 |
| 0x00018000 | 581 | 밉 체인이 있는 텍스처 → **bit15 = 밉맵 사용** |
| 0x00510000 | 368 | 하늘 타일(`Athn01B_G000`), 한글 폰트 `GOWK_*`, HUD → 클램프 계열 추정 |
| 0x005D0000 | 75 | HUD 아이콘, 하늘 타일 |
| 0x00410000, 0x00110000, 0x00118000, 0x00518000 | 소수 | |

## 4. MAT_ (매직 0x08, 관찰된 태그 flags=6)

크기 = `0x38 + 0x40 × layerCount` (120 / 184 / 248 바이트 = 레이어 1/2/3, 각각 10991 / 231 / 13 개).

### 헤더
| 오프셋 | 타입 | 필드 | 의미 |
|-------|------|------|------|
| 0x00 | u32 | magic | `0x00000008` |
| 0x04 | u32 | — | 항상 0 |
| 0x08 | f32[3] | color | 대부분 (0.8, 0.8, 0.8). 디퓨즈 색 추정 |
| 0x14 | f32 | param14 | 0 또는 0.5 (Kratos 피부/옷 0.5). 스펙큘러/환경 강도 추정 |
| 0x18 | f32[4] | — | 항상 0 |
| 0x28 | f32 | param28 | 항상 1.0 |
| 0x2C | f32 | specPower | 0, 2, 20, 64(피부), 100(옷)… 스펙큘러 지수 추정 |
| 0x30 | u32 | param30 | 대부분 1 (0 인 것 296개) |
| 0x34 | u32 | layerCount | 1~3 — 크기와 정확히 일치해서 확정 |

### 레이어 (0x40 바이트)
| 오프셋 | 타입 | 필드 | 의미 |
|-------|------|------|------|
| 0x00 | u32 | renderFlags | **bit24–31 = GS ALPHA 레지스터 하위 8비트** (A,B,C,D 각 2비트) |
| 0x04 | u32 | flags2 | 0, 0x100, 0x8, 0x108, 0x80000000, 0x10000000 |
| 0x08 | u32 | mask1 | 하위 24비트 렌더 플래그의 반전 마스크로 추정 (0x44010080 ↔ 0xFEFF7B) |
| 0x0C | u32 | mask2 | 항상 `~flags2` |
| 0x10 | char[24] | texture | TXR_ 이름 (빈 문자열 = 텍스처 없음, 예: `MAT_ClothCollisionMat`) |
| 0x28 | f32[4] | rgba | 레이어 색 배율 (1.0, 1.5, 2.0 …) |
| 0x38 | f32 | param38 | 1.0 / 두 번째 이후 레이어는 0.25 가 흔함 |
| 0x3C | u32 | — | 0 |

GS ALPHA 블렌드 식 `((A - B) * C >> 7) + D` (A,B,D: 0=Cs 1=Cd 2=0, C: 0=As 1=Ad 2=FIX)

| 상위 바이트 | A B C D | 식 | 의미 |
|-----------|---------|----|------|
| 0x44 | Cs Cd As Cd | (Cs-Cd)·As + Cd | 일반 알파 블렌드 (가장 흔함) |
| 0x48 | Cs 0 As Cd | Cs·As + Cd | 가산 (이펙트: 불꽃, 빛) |
| 0x42 | 0 Cs As Cd | Cd - Cs·As | 감산 |
| 0x01 | Cd Cs As Cs | (Cd-Cs)·As + Cs | 반전 블렌드 (멀티 레이어 2·3번째) |

가산(0x48) 레이어는 하위 바이트가 0x09 (`0x48090080`) 로 0x01 대신 0x08 비트가 추가로 서 있다 → Z 쓰기 끔 등으로 추정.

## 5. 디코딩 알고리즘 요약
1. TXR → GFX, PAL 이름 해석 (태그 위치 기준 가장 가까운 앞쪽 리소스). PAL 이 비어 있으면 nextMip 로 자신을 가리키는 상위 TXR 의 PAL 을 사용.
2. 인덱스 읽기: PSMT4 → 선형 니블(하위 먼저). PSMT8 → `flags & 2` 면 선형, 아니면 위 스위즐 식.
3. CLUT 조회: 256색이면 CSM1 인덱스 변환, CLUT 번호 c 는 `c * colors` 엔트리부터.
4. 알파 0..0x80 → 0..255.
5. frames>1 이면 결과는 세로 스트립 (프레임 높이 = height / frames).

## 6.1 추가 해석 (16 문서 §3)
- 애니메이션 프레임(frames > 1)은 MAT 그룹의 ANM type 9 키가 고른다 (TXR/MAT 필드 무관). UV 스크롤은 ANM type 8.
- 0x44 머티리얼 대부분은 **불투명 + 알파 테스트(≥ 0.75)** 이고, 정렬(반투명) 대상은 p28/p38 ≠ 1, TXR bit18, 0x48/0x42 뿐 (0x1537C8, 0x165998).
- 레이어 바이트 0x01 = `(Cd−Cs)·As+Cs` → GL `ONE_MINUS_SRC_ALPHA, SRC_ALPHA`. renderFlags bit19 = 깊이 쓰기 끔, bit7 = 텍스처, bit1 (0x02) = 환경맵 VU 경로 (법선 →
  카메라 공간 구면 UV, 첫 레이어 포함), bit2 (0x04) = 머티리얼 색 (16 §3.3, 43 §25.2 — 발리스타 틀 `MAT_M02MetalTrim01b` rf 0x86 의 크롬 공 텍스처).

## 7. 미해결 질문
- **폭 8 픽셀 PSMT8 (flags=0)** 13개(`TXR_rope022` 8x8, `TXR_miscRopeSection2` 8x32): 선형·스위즐·다른 전송 사각형(1x16…16x1) 어느 것도 상위 밉과 맞지 않음. 현재는 스위즐 식으로 읽고 범위 밖은 인덱스 0.
- 높이가 4의 배수가 아닌 텍스처(256x62, 128x31, 64x15): 스위즐 식이 데이터 범위를 넘는 픽셀이 생김 (마지막 1~2행). 실제 전송 방식 미확인.
- GFX flags=2 가 R_PERMK 에만 있는 이유 (상주 리소스 로더가 다른 경로로 업로드?).
- TXR `mipL`, `flags` 의 bit18–22 정확한 의미 (클램프/필터?) → 실행 파일의 TXR 로더에서 GS TEX1/CLAMP 레지스터 조립부를 찾아 확인 (06 문서).
- MAT 헤더 param14/specPower/param30, 레이어 flags2/mask1/param38 의 정확한 의미 → 렌더러 분석 필요.
- CLUT 2개 팔레트의 두 번째 CLUT 선택 조건 — 석화 효과는 아니다 (석화 = 별도 석상 GO + 돌 텍스처, 35 §2.2). 사용처 [미확인].

## 부록: 2 의 거듭제곱이 아닌 텍스처와 UV [확실]
GS 는 TEX0 TW/TH(2 의 거듭제곱) 크기로 샘플링하고 메시 ST(UV) 도 그 크기 기준이다. GFX 데이터 높이가 그보다 작은 텍스처
(HUD 32×24, 256×96, 128×80 …, 레벨 FLP 의 히드라 미터 512×72) 는 UV 최댓값이 정확히 `실제 높이 / 2^TH` (0.75, 0.744, 0.62, 0.558) 로 끝난다.
엔진 `Texture.of` 는 이런 이미지를 다음 2 의 거듭제곱 크기로 투명하게 덧대 올린다 (이전에는 세로로 늘어나 위쪽만 보였음 — HUD 왼쪽 원형 아이콘, 히드라 미터 테두리).
